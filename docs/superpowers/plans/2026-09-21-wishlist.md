# Wishlist Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a surgical Wishlist feature where every authenticated user manages their own improvement requests and admins manage the complete list.

**Architecture:** Add one isolated Supabase table with explicit RLS, one typed browser data-access module, and one `/wishlist` page shared by regular users and admins. Expose it through the authenticated header navigation only and a narrow `/wishlist` route rule; do not modify procurement workflows or existing business tables.

**Tech Stack:** Next.js App Router, React client components, Supabase browser client, TypeScript, existing shared UI components, Node test runner.

## Surgical constraints and risks

- Keep all wishlist code under `/wishlist`, `lib/wishlist.ts`, `types/wishlist.ts`, `components/wishlist/`, and one migration/test group.
- Do not reuse `bug_reports`; wishlist ideas have different ownership, statuses, and admin semantics.
- Do not alter the existing `bugtrack` route, admin dashboard stats, audit schema, or notification tables for the MVP.
- Keep the route available to every `AppRole`, including supplier, even if a module-visibility row is later added; direct route access remains the source of truth for the requirement.
- The plan assumes `profiles.active` is enforced by the existing middleware and that admin is represented by `role.name = 'admin'`.
- If live RLS cannot be exercised locally, stop before claiming deployment readiness and report the unverified boundary explicitly.
